# 自动化口语 → 设备与流程语义

本文件是用户授权的设计默认，不是对现场硬件的事实声明。优先级：当前明确要求 > 现有工程中已确认的设备/接口 > 本默认。默认能覆盖的常规问题直接继续，不反复追问；在程序说明中集中列出采用的假设。

## 气缸

“一个气缸推出”默认识别一个气缸设备：

- 对象名遵循工程命名；新工程可按出现顺序 Cyl01、Cyl02。
- Home 为原位/缩回，Work 为工作位/伸出。
- 两到位输入 HomeSensor、WorkSensor，默认 TRUE 到位。
- 两控制输出 HomeValve、WorkValve，双线圈，不将断开 Work 当作自动缩回。
- CmdHome、CmdWork 请求，PermitHome/PermitWork 互锁，AtHome/AtWork、Busy、Fault/FaultID 状态。
- 双命令冲突、双到位冲突、动作超时需诊断；两控制输出不得同时 TRUE。
- 不自动推断阀的断电安全状态。安全条件由独立安全系统决定，普通流程许可不能冒充安全输入。
- 到工作位即完成“伸出”这个设备动作；是否还需确认物件离开属于工艺步骤，不能硬塞进气缸 FB。

明确“单线圈、弹簧回位、无到位开关”等时覆盖默认，使用匹配的设备实现，不继续套用双线圈模板。

## 皮带到位后气缸推出

默认识别：皮带 Run 控制、目的位置传感器、气缸。根据现有命名与上下文复用同一个到位传感器，不为同一句话凭空增加多个传感器。

到位信号 TRUE 的逻辑扫描：撤销皮带 Run，并提出气缸 CmdWork。**不默认等待到位传感器变 FALSE，不默认插入停稳定时器，也不要求下一扫描才提出气缸命令。**设备许可仍有效；若现场模板提供机械停止反馈、危险区互锁等已确认约束，应保留并解释。

同一扫描下发命令不意味着机械零时间停稳。用户明确要求停稳、定位到位或延时后动作时，才将对应等待加入工艺。

程序段先算步骤转移，再按新步骤生成设备命令，最后调用设备 FB/映射输出，避免“先输出后转移”造成隐含的一扫描延迟。同一实例每周期调用一次，不靠在 CASE 各分支重复调用设备FB实现。

## 其他语义

- “同时”：共同触发、允许并行；定义两动作完成的汇合条件。
- “到位并检测有料”：通常是两个状态同时成立，不是要求两个上升沿同一扫描。
- “回原位”：发出 Home 动作请求并检查 Home 到位；不得默认断电就回位。
- “物件没了”：按上下文确定哪一个物件传感器清空，不等于所有传感器清空，也不等于气缸已回位。
- “等待下一件”：定义新件触发/重入条件；不能把前一个物件持续信号反复当作新件。
- 伺服轴号、位置单位、电子齿轮和物理接线不从口语猜测。离线示例可以使用明确标注的参数，现场绑定从工程获取。

## 程序分工

程序段持有工艺 Step、转移条件、循环状态、跨设备协调。FB 封装设备能力，如双控气缸、输送驱动、轴定位；其内部可以有边沿、超时和功能动作状态，但不含“输送→移载→推料→下一件”这种整机步序。

`assets/PRG_Sequence.st` 展示同一扫描停止输送与请求推出，`assets/FB_Cylinder2Coil.iec` 是单个气缸功能模板。示例不等于已经自动生成完整工程。沿用已有框架时优先用已有合适 FB/ST，而不是强迫替换成这些模板。

## 设备接口脚本

模型先理解自然语言和工程上下文，输出设备清单，再运行 `scripts/expand_devices.py input.json output.json`。脚本负责确定性的默认补全，不声称能靠关键词完整理解工艺。

输入示例：

```json
{"devices":[{"name":"Cyl01","kind":"cylinder"},{"name":"Belt01","kind":"belt"}]}
```

每个设备可用 `overrides` 明确覆盖默认。如工程已确认单线圈，应覆盖 valve，并选择相应实现；双线圈模板只适用于其匹配的接口。输出保留默认来源与覆盖记录，不写死物理模块/地址。
