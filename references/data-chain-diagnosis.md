# 原平台数据链排查

用于用户指定保留既有“实时监控/历史查询”等画面，而 PLC 已发新协议但页面无数据的情况。不要用新页面或旁路服务代替原平台验收。先固定本次使用的 PLC 程序、协议版本、采集配置和部署路径，防止拿旧文件解释新日志。

## 按同一条报文逐段追踪

1. **采样与组包**：核对触发窗口、采样点数、分包序号、末包标记和曲线标识。包序号可以每包重置；若协议要求 `TimeCount` 表示整条曲线的采样时间，它必须跨包连续，不能每包从 1 重来。确认丢点、环满和中途复位没有被伪装为连续曲线。
2. **时间基准**：核对 PLC 实际任务设置、在线监视的实际周期、传给采集 FB 的周期值，以及报文的采样间隔/时间计数。把配置的 10 ms 写成真实 1 ms，接收端可能把整条曲线的时长或相邻点位置判错；改 XML 或画面无法修复源时间错误。若想程序读取自身任务周期，先查目标 CPU Unit Version 对该指令的支持，实机编译并验证单位和整毫秒约束；不支持时显式配置并在投产注释与验收表中要求核对。
3. **Broker 实收**：在订阅端保存 Topic、原始字节、长度、接收时刻和帧摘要。PLC 入发送队列、socket 完成、MQTT ACK、业务系统接受是不同阶段。没有原始帧时，先解决地址、端口、Topic、认证和订阅时序，勿先改后端字段。
4. **解析与映射**：用同一原始帧逐字节核对 XML 的偏移、宽度、字节序、数组长度、保留字段及单位，再检查模板（如 `.vm`）是否把所有业务身份字段映射到平台需要的名称和类型。建立“PLC 字段→平台字段→数据库键/查询条件”对照表；产品号、配方号、门类型等名称相似也不能自行互换。新增字段还要检查下游流处理的字段顺序，避免后续列整体错位。
5. **页面与历史**：用报文的唯一身份和时间范围查看入库记录、实时推送及原页面查询条件。实时有值而历史没有，优先查入库和查询键；历史有值而实时没有，查推送订阅和过滤。设备关系由现场确认；不能因库中旧数据能查到就认为新报文映射正确。

每段记录一条可复核证据：报文或日志时间、Topic/长度、解析后关键字段、入库键或页面请求。找到首个数据变化或丢失点后修该处，同时回归实时与历史。用户允许舍弃旧数据时可只验证新记录，但仍要确认旧格式兼容是否是当前要求。
